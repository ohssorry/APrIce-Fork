## C-002 — JSON 출력 형식 추가

**왜 먼저 하는가.** C-003(비용 델타)과 C-004(GitHub Action)가 둘 다 **스캔
결과를 기계가 읽어야** 합니다. 지금은 터미널 텍스트와 마크다운뿐이라, 두 결과를
비교하려면 문자열을 다시 파싱해야 합니다. **JSON이 없으면 C-003이 지저분해집니다.**

**할 일**
- `report.py`에 `render_json(result: ScanResult) -> str`
- `cli.py`의 `--format` 선택지에 `json` 추가
- 스키마에 **버전 필드를 넣으세요** (`"schema_version": 1`). 나중에 형식이
  바뀔 때 소비자가 대응할 수 있습니다

포함할 내용: 호출별 위치·프로바이더·모델·`max_tokens`·`loop_depth`,
비용 범위, 합계, findings 전체, unpriced 목록.

**주의.** `report.py`의 함수들은 **순수 함수**입니다 — 문자열을 반환할 뿐
출력하지 않습니다. 이 규칙을 지키세요. 테스트가 쉬운 이유가 이겁니다.

**완료 조건**
- [ ] `aprice scan src/ --format json` 이 유효한 JSON 출력
- [ ] `json.loads()`로 파싱되는지 테스트
- [ ] `schema_version` 포함
- [ ] 호출이 0건일 때도 유효한 JSON (빈 배열)
- [ ] `pytest` · `ruff check .` 통과

## C-003 — PR 비용 델타 (`aprice diff`)

**이게 프로젝트의 최대 차별점입니다.** README 첫 줄이 "estimate what your API
calls cost — **before you merge them**"인데, 정작 **머지 전후를 비교하는 기능이
없습니다.** 지금은 단순 스캐너일 뿐입니다.

Infracost가 IaC에서 한 일을 LLM API 영역에서 하는 지점이고, 혁신성 6점이
걸린 기능입니다.

**할 일.** 두 스캔 결과를 비교하는 명령을 만듭니다.

```console
aprice diff --base main --head HEAD
```

출력 예시:

```
APrIce: cost delta vs main

  + src/batch.py:31   claude-opus-5    +$0.10740 per request   [new]
  ~ src/summarize.py:16  sonnet -> opus  +$0.08920 per request
  - src/old.py:12     claude-haiku-4-5  -$0.00120 per request  [removed]

  Net change: +$0.19540 per request
  ! 1 new cost risk introduced: [call-in-loop] src/batch.py:31
```

**구현 방향.**
- `git worktree` 또는 `git stash`로 base 리비전을 별도 경로에 꺼내 스캔합니다.
  **작업 트리를 건드리지 마세요** — 사용자의 미커밋 변경을 날리면 끝장입니다
- 호출을 무엇으로 동일 호출로 볼지 정해야 합니다. `파일:줄번호`는 위쪽에 줄이
  추가되면 전부 어긋납니다. **`파일 + 프로바이더 + 모델` 조합**이 더 안정적입니다.
  완벽할 필요 없습니다 — 판단 근거를 주석으로 남기세요
- 비교 로직은 **새 모듈**(`src/aprice/diff.py`)로. `report.py`에 밀어넣지 마세요

**범위 제한.** 델타는 **요청당 비용의 변화**입니다. "이 PR이 월 $X를 더 씁니다"는
여전히 말하지 않습니다. 호출 횟수를 모르는 건 diff에서도 똑같습니다.

**완료 조건**
- [ ] 추가 / 변경 / 삭제 세 경우 모두 처리
- [ ] 새로 생긴 warn 등급 finding이 별도 표시됨
- [ ] 사용자의 미커밋 변경이 보존됨 (테스트로 확인)
- [ ] `--format json` / `markdown` 지원
- [ ] `pytest` · `ruff check .` 통과

> 어려운 작업입니다. **C-005(보고서 뼈대)를 먼저 만들어두고** 시작하세요.
> 여기서 시간이 녹아도 제출물이 비지 않도록.

## C-004 — GitHub Action 패키징

**목표.** PR을 열면 봇이 비용 리포트를 댓글로 답니다. **시연 영상의 하이라이트가
될 장면입니다.**

**할 일**
1. 저장소 루트에 `action.yml` (composite action)
2. `.github/workflows/pr-cost.yml` — PR 이벤트에서 `aprice diff` 실행 후
   `--format markdown` 결과를 PR 코멘트로
3. **댓글을 매번 새로 달지 말고 기존 댓글을 갱신하세요.** PR에 커밋 10번 하면
   댓글 10개가 쌓입니다. 봇 댓글에 숨은 마커(`<!-- aprice -->`)를 넣고 찾아서
   업데이트하는 방식이 표준입니다
4. 입력 파라미터: `path`, `input-tokens`, `fail-on-warning`
5. **우리 저장소 자체에 적용하세요.** 자기 도구를 자기 PR에 쓰고 있다는 게
   심사위원에게 가장 강력한 증거입니다

**권한 주의.** `permissions: pull-requests: write`가 필요합니다. 포크에서 온
PR은 토큰 권한이 제한되므로, 그 경우 실패하지 말고 **조용히 건너뛰도록** 하세요.

**완료 조건**
- [ ] `action.yml` 작동
- [ ] PR 코멘트가 달리고, 재실행 시 **갱신**됨 (중복 안 됨)
- [ ] 우리 저장소의 실제 PR에 리포트가 붙은 스크린샷 확보 → **README에 삽입**
- [ ] 포크 PR에서 권한 오류로 CI가 빨갛게 되지 않음

> 스크린샷은 평가 체크리스트에 명시된 항목입니다("README: … PR 코멘트
> 스크린샷"). 반드시 남기세요.

2. **기존 도구와의 차이** — `.prompt` 파일이 아니라 **소스코드를 직접 파싱**
   (onboarding.md의 비교표 재사용)
3. **접근 방법** — AST 정적 분석. 정규식으로 불가능한 3가지

   심사위원이 "월 비용은 어떻게 예측하나요"라고 물으면
   **"예측하지 않습니다. 할 수 없기 때문입니다"**가 우리 답입니다
6. **오픈소스 전략** — 가격표를 YAML로 분리해 비개발자도 PR 가능한 구조
7. **팀 운영** — 이슈/PR/리뷰 통계, 역할 분배
8. **한계와 향후 계획** — `docs/architecture.md` 5절 재사용
