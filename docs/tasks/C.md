# 담당 C(예은) - 출력·CI·문서 단기간 계획

> 엑셀 역할표의 `WEB-01`~`WEB-05`를 현재 Python 구조에 맞게 옮긴 계획입니다.
> 8월 29일 기능 동결 전에는 결과를 사람이 이해하고 기계가 재사용할 수 있게
> 만들고, 제출 문서를 빈칸 없이 준비하는 데 집중합니다.

## 소유 파일

```text
src/aprice/report.py
src/aprice/cli.py
.github/
docs/
README.md
CONTRIBUTING.md
```

- A 소유인 `detector.py`, `rules.py`는 수정하지 않습니다.
- B 소유인 `pricing.py`, `prices/*.yaml`은 수정하지 않습니다.
- 공용 파일 `models.py`가 필요하면 코드를 바꾸지 말고 먼저 이슈로 제안합니다.

## 이번 기간의 완료 기준

- README만 보고 설치·실행·문서 이동이 가능합니다.
- 텍스트와 Markdown 외에 유효한 JSON 결과를 출력합니다.
- 결과보고서와 시연 영상 대본의 뼈대가 준비됩니다.
- 전체 `pytest`, `ruff check .`, `ruff format --check .`가 통과합니다.

## 필수 작업

| 순서 | 작업 | 완료 조건 |
|---|---|---|
| C-01 | README 신뢰 정보 정리 | 실제 clone 주소, CI·Python·라이선스 배지, 아키텍처 링크 |
| C-02 | JSON 출력 추가 | `schema_version`, 호출·비용 범위·finding·미가격 목록 포함 |
| C-03 | 결과보고서 뼈대 작성 | 문제·차별점·방법·아키텍처·설계 원칙·팀 운영·한계 포함 |
| C-04 | 시연 영상 대본 작성 | 장면별 화면·대사·시간과 녹화 준비 체크리스트 포함 |

### C-01 - README 신뢰 정보 정리

저장소 주소와 설치 순서를 실제 상태에 맞추고, CI·Python·MIT 배지를 추가합니다.
가격 지원 표는 B의 가격 PR이 머지된 뒤에만 갱신합니다. 문서의 내부 링크도 함께
확인합니다.

### C-02 - JSON 출력 추가

`report.py`의 렌더러는 출력하지 않고 문자열만 반환하는 순수 함수로 유지합니다.
JSON에는 `schema_version: 1`, 호출 위치, 제공자, 모델, 토큰 설정, 루프 깊이,
비용의 `low`와 `high`, findings, unpriced 목록을 포함합니다. 호출이 0건이어도
유효한 JSON이어야 합니다.

### C-03 - 결과보고서 뼈대 작성

기존 `docs/onboarding.md`, `docs/architecture.md`, `docs/methodology.md`에서 근거를
재사용합니다. 특히 월 비용을 예측하지 않는 이유를 미완성이 아니라 정직한 설계
경계로 설명합니다. 제출 마감과 공식 분량은 확인 전까지 추측해 적지 않습니다.

### C-04 - 시연 영상 대본 작성

3~5분을 기준으로 AST 탐지, 오탐 방지, 요청당 비용 범위, 월 비용을 추정하지 않는
이유, YAML 가격표를 보여줍니다. 실제 제한 시간이 확인되면 그 기준을 우선합니다.

## 시간이 남을 때만

- `aprice diff --base main --head HEAD` 최소 버전
- PR에 요청당 비용 변화 댓글을 갱신하는 GitHub Action

이 두 작업은 가치가 크지만 서로 의존합니다. 필수 작업이 끝나고 테스트할 시간이
확보된 경우에만 별도 이슈로 시작합니다.

## 전원 공통 - 통합·릴리스

엑셀 역할표의 `INTEGRATION-01`, `RELEASE-01`은 세 명이 함께 수행합니다.

1. 담당자는 이슈를 만들고 자기 소유 파일만 수정합니다.
2. `main`을 최신화한 뒤 작업별 브랜치를 만듭니다.
3. `pytest`, `ruff check .`, `ruff format --check .`를 통과시킵니다.
4. 한글 커밋을 의미 있는 단위로 나눠 push합니다.
5. `develop` 대상 PR을 올리고 다른 담당자 1명의 승인을 받습니다.
6. 기능 동결 뒤에는 새 기능 대신 보고서·영상·문서와 회귀 수정만 진행합니다.

## 작업 단위

각 행을 별도 이슈와 별도 `feat/...` 또는 `docs/...` 브랜치로 진행합니다.
PR 본문에 변경 이유와 검증 결과를 적고, 승인 1명 전에는 머지하지 않습니다.
