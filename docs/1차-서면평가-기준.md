## 핵심 시사점

1. **배점이 완전 균등하다.** 코드 품질 하나만 잘해도 최대 6/30점이다. 5개 축을 고르게 채우는 팀이 이긴다.
2. **평가 대상의 절반은 코드가 아니다.** 결과보고서 + 시연 영상이 소스코드와 동급의 제출물이다. 개발 막판에 몰아서 만들 대상이 아니다.
3. **팀워크는 GitHub 활동 로그로 증명된다.** Issues / PR / review / merge 이력 자체가 채점 근거로 명시되어 있다. 개발 첫날부터 이슈 기반으로 작업해야 하며, 마지막에 커밋 몰아치기를 하면 이 6점은 회수 불가능하다.
4. **1차는 "2배수 내외 선발"이다.** 최종 수상이 아니라 통과가 목표. 감점 요인을 없애는 것이 화려한 기능 추가보다 효율적이다.

## APrIce 프로젝트 대응 체크리스트

### 프로젝트 구조 및 코드 완성도 (6점)
- [ ] 파서 / 가격 DB / 리포터 모듈 분리 (책임 경계가 눈에 보이게)
- [ ] 핵심 로직에 테스트 작성 — "제 기능을 하는 정도"의 가장 싼 증명
- [ ] 린터 + 포매터 CI 적용
- [ ] 주석은 "무엇"이 아니라 "왜"를 남길 것 (평가항목에 주석 활용도가 명시됨)

### 오픈소스 프로젝트로의 발전 가능성 (6점)
- [ ] LICENSE (MIT 등) 명시
- [ ] CONTRIBUTING.md — 특히 **가격 DB(YAML)를 외부인이 PR로 갱신하는 절차**. 이게 APrIce의 가장 강력한 발전 가능성 서사다
- [ ] `good first issue` 라벨이 붙은 이슈 몇 개 실제로 등록
- [ ] 플러그인 구조 (새 API 프로바이더 추가 방법 문서화)

### 개발 문서의 구체성 (6점)
- [ ] README: 문제 정의 → 설치 → 30초 사용 예시 → PR 코멘트 스크린샷
- [ ] 아키텍처 문서 (다이어그램 1장)
- [ ] **비용 추정 방법론과 그 한계를 명시한 문서** ← 정직하게 쓸수록 신뢰도가 올라가는 항목
- [ ] 결과보고서 (제출 필수 자료)

### 프로젝트 혁신성 (6점)
- [ ] AST 기반 정적 분석 (정규식이 아님을 문서에 명시)
- [ ] PR diff 기반 **비용 델타** 산출 — Infracost가 IaC에서 한 것을 API/LLM 영역에서 처음 하는 지점
- [ ] 임계값 초과 시 CI 실패 기능

### 프로젝트 팀워크 (6점)
- [ ] 오늘부터 모든 작업을 GitHub Issue로 생성
- [ ] 직접 push 금지, PR + review 후 merge를 규칙으로
- [ ] 마일스톤 / 프로젝트 보드 운영
- [ ] 커밋 컨벤션 합의 및 문서화
